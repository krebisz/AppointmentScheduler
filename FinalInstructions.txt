## 1. Inspect before changing

Inspect:

- The complete repository tree, current Git diff, `git status`, and `git ls-files`.
- Projects, project references, NuGet packages, configuration, migrations, generated artifacts, source, tests, and documentation.
- The complete request path through API, Application, Domain, and Infrastructure.
- Ignored and untracked files that could accidentally be submitted or reveal internal working material.

Do not delete an uncertain file merely because it appears unused. List uncertain candidates as proposed removals instead.

## 2. Apply the justification test

For every non-trivial component, retain it only when it has a clear justification based on at least one of these:

1. It directly implements an assessment requirement.
2. It protects a domain invariant or data-integrity rule.
3. It establishes a necessary dependency or infrastructure boundary.
4. It materially improves testability or substitutability.
5. It makes the implementation simpler or clearer overall.

Identify code that is technically used but unnecessarily bulky, difficult to defend, or inconsistent with the stated architecture. Simplify it only when the change is low-risk and makes the design easier to explain.

## 3. Remove or simplify unjustified code

Remove or simplify, where clearly safe:

- Remaining template or sample code.
- Unused files, types, methods, DTOs, interfaces, imports, packages, and project references.
- Empty, speculative, or single-use abstractions that add indirection without meaningful separation.
- Generic repositories or wrappers that merely duplicate EF Core without expressing a useful boundary.
- Premature extensibility, configuration, or infrastructure not exercised by the solution.
- Duplicate mapping, validation, or error-handling logic where low-risk consolidation improves clarity.
- Excessive generated-style comments, comments that only restate code, stale TODOs, and abandoned alternatives.
- Documentation that describes planned behavior as implemented.

## 4. Audit and remove non-code submission clutter

Delete files that clearly should not form part of the employer submission, including (EXCEPT WHERE THEY MAY HAVE EXPLANATORY VALUE FOR THE REVIEWER OR USER):

- AI prompts, agent instructions, coaching notes, evaluation reports, scratch material, and internal workflow artifacts intended only to guide implementation.
- Obsolete or superseded specifications and documents.
- Template/sample HTTP files or documentation that no longer represents the implemented API.

Update `.gitignore` with precise rules for local/generated clutter that may recur. Do not use broad rules that hide legitimate source, Markdown, migrations, tests, generated-client deliverables, or required configuration. Remember that `.gitignore` does not untrack an already tracked file; inspect `git ls-files` and untrack exact unwanted files while retaining local copies only when they are still needed.

Preserve non-code files that genuinely serve the submitted solution, including:
